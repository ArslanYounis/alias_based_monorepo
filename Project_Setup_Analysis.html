Cross-Platform UI Components Monorepo – Project Setup Analysis

1. Executive Summary

This monorepo enables a single codebase to deliver UI components for both web (Vite + React) and mobile (Expo / React Native). The key mechanism is the @platform path alias, which resolves to platform-specific implementations at build time. Shared components under shared/components/ import from @platform/Container, @platform/Text, etc., and the bundler (Vite for web, Metro for mobile) resolves these to the correct implementation. This design reduces duplication of business logic while allowing platform-native rendering (HTML/CSS vs React Native).

2. Project Overview and Architecture

The project uses npm workspaces with two primary packages: web and mobile. A shared folder (not an npm workspace) holds types, hooks, and composite components that use @platform imports. The architecture follows this flow:

  1. Platform primitives: Each named component (e.g., Buttons, Container, Text) exists in both web/src/ui/ and mobile/src/ui/ with the same props contract but different implementations (HTML vs React Native).
  2. Shared prop types: All prop interfaces live in shared/types/ui/, ensuring web and mobile stay in sync.
  3. Shared composite components: Components like DummyComponent, LargeComponent, and PlotSearch live in shared/components/ and import from @platform/*. At runtime, the correct platform implementation is used.

4. Path Aliases and Resolution

Path aliases are configured at three levels: root tsconfig, web tsconfig, mobile tsconfig, and the respective bundlers (Vite, Metro).

AliasWeb ResolutionMobile Resolution
@platform/*web/src/ui/*mobile/src/ui/*
@shared/*../shared/*../shared/*
@/*./src/* (web only)—
~/*—./* (mobile root)

Web (Vite): vite.config.ts uses resolve.alias to map @platform to web/src/ui and @shared to ../shared. The vite-tsconfig-paths plugin also respects tsconfig paths.

Mobile (Metro): metro.config.js sets resolver.extraNodeModules so that @platform resolves to mobile/src/ui and @shared to ../shared. The watchFolders includes ../shared so Metro can resolve imports from the shared folder.

5. How the @platform Alias Works

When a shared component (e.g., shared/components/DummyComponent/DummyComponent.tsx) imports:

import { Container } from "@platform/Container";
import { Text } from "@platform/Text";
import { Buttons } from "@platform/Buttons";

The resolution depends on which app is running:

  • Web: When the web app builds or runs, Vite resolves @platform/Container → web/src/ui/Container, @platform/Text → web/src/ui/Text, etc. The shared component thus uses web-specific implementations (HTML elements, Tailwind CSS).
  • Mobile: When the mobile app builds or runs, Metro resolves @platform/Container → mobile/src/ui/Container, etc. The same shared component now uses React Native components (View, Text, TouchableOpacity).

The shared component code is identical; only the resolution target changes. This is the core benefit of the @platform alias.

Shared Folder TypeScript

The shared folder has its own tsconfig.json with:

"paths": {
  "@platform/*": ["./__platform_types__/*"],
  "@shared/*": ["./*"]
}

For type-checking shared code in isolation, @platform resolves to shared/__platform_types__/, which contains generated stub declaration files (e.g., Buttons.d.ts) that unify the prop types from both web and mobile implementations.

6. Shared Types and Prop Contracts

Each platform primitive has a corresponding type file in shared/types/ui/, e.g., Buttons.ts:

export interface ButtonsProps {
  language?: "en" | "ar";
  size?: "s" | "m" | "l";
  fullWidth?: boolean;
  title?: string;
  title_ar?: string;
  leftIcon?: ReactElement;
  rightIcon?: ReactElement;
  disabled?: boolean;
  type?: "primary" | "secondary" | "tertiary" | "text-link" | "delete";
  buttonType?: "button" | "submit" | "reset";
  onClick?: () => void;
  iconColor?: string;
  tooltip?: { ... };
}

Both web and mobile Buttons components import from @shared/types and implement this interface. Platform differences (e.g., web uses onClick, mobile may map to onPress internally) are handled inside each implementation while keeping the external API consistent.

Mobile library build: mobile/scripts/build-lib.js compiles lib-index.ts and then post-processes the output to replace @platform/* and @shared/* imports with relative paths. This ensures the published package does not depend on path aliases at consumer install time.

8. Adding New @platform Components – Step-by-Step

To add a new cross-platform component (e.g., NewWidget), the developer must:

  1. Create shared type: Add shared/types/ui/NewWidget.ts with the props interface.
  2. Export from shared types: Add export * from "./NewWidget" in shared/types/ui/index.ts.
  3. Implement web version: Create web/src/ui/NewWidget/NewWidget.tsx and index.ts, importing types from @shared/types.
  4. Implement mobile version: Create mobile/src/ui/NewWidget/NewWidget.tsx and index.ts with the same props contract.
  5. Regenerate platform types: Run npm run generate:platform-types to create/update shared/__platform_types__/NewWidget.d.ts.
  6. Re-export from library entry points: Add export { NewWidget } from "./src/ui/NewWidget" (or equivalent) in both web/index.ts and mobile/lib-index.ts.
  7. If used in a shared component: Import via @platform/NewWidget in the shared component.

This is a seven-step process with multiple touchpoints (types, web, mobile, platform types, library exports).

9. Complexity Analysis

9.1 Architectural Complexity

The @platform pattern introduces several layers of indirection:

  • Dual resolution: @platform means different things in web vs mobile. A developer must understand that the same import resolves to different files depending on the build context.
  • Three-way TypeScript config: Root, web, mobile, and shared each have path mappings. Misconfiguration in one place can cause silent failures or confusing errors.
  • Generated types: shared/__platform_types__/ is generated by a script. Forgetting to run it after adding a component can lead to TypeScript errors in shared code.
  • Build-time alias rewriting: The mobile build script rewrites aliases in the output. This is non-standard and adds maintenance burden.

9.2 Synchronization Requirements

For each @platform component:

  • Web and mobile must maintain identical public props and semantics.
  • Any change to props requires updating shared/types, both implementations, and possibly generate-platform-types output.
  • Platform-only features (e.g., web-specific Layout) are allowed but increase the cognitive load when deciding what belongs in @platform vs platform-specific exports.

9.3 Tooling and Build Configuration

Each platform uses different tooling:

  • Web: Vite, tsconfig paths, vite-tsconfig-paths
  • Mobile: Metro, extraNodeModules, Expo
  • Shared: Custom tsconfig with __platform_types__ resolution

Adding a new build target (e.g., another platform) would require another alias resolution layer.

10. Impact on Development Time

10.1 Per-Component Effort

Adding a single @platform component takes roughly 2–4× the time of adding a web-only or mobile-only component because:

  • Two full implementations (web + mobile) must be written and tested.
  • Shared types must be defined and kept in sync.
  • Platform type generation and library exports must be updated.

10.2 Ongoing Maintenance

Every change to a shared component or platform primitive can require:

  • Updating shared types
  • Updating both web and mobile implementations
  • Regenerating platform types
  • Testing on both web and mobile

Estimated overhead: 20–40% compared to a single-platform codebase, depending on how often components change.

10.3 Debugging Complexity

When a bug appears in a shared component:

  • It may manifest differently on web vs mobile (e.g., different event handlers, layout engines).
  • The developer must trace through alias resolution to know which implementation is actually running.
  • IDE "Go to Definition" may land in __platform_types__ stubs instead of real implementations, which can confuse newcomers.

11. Unit Testing Headaches

Unit testing @platform components introduces significant overhead and complexity that can increase as the component library grows.

11.1 Dual Test Suites

Because each component has two implementations (web and mobile), teams often end up maintaining two parallel test suites. Web components use React Testing Library with jsdom or similar; mobile components require React Native Testing Library with a different renderer. Shared components that use @platform imports must be tested in both environments—or with complex mocking—to ensure correct behavior on each platform.

11.2 Alias and Module Resolution in Tests

Test runners (Jest, Vitest, etc.) must resolve @platform and @shared the same way the app does. This requires:

  • Configuring moduleNameMapper or equivalent in Jest/Vitest to map aliases for web tests
  • Ensuring Metro or the mobile test runner resolves aliases for React Native tests
  • Shared tests may need different resolver configs depending on which platform they target

Misconfiguration leads to "module not found" or wrong implementations being loaded, which can be time-consuming to debug.

11.3 Mocking Complexity

When testing shared components (e.g., PlotSearch, DummyComponent), developers must decide whether to mock @platform components or use real implementations. Mocking requires setting up module mocks for each platform primitive used; using real implementations may pull in platform-specific dependencies (e.g., React Native or DOM APIs) that fail in the other platform's test environment.

11.4 Platform-Specific Behavior

Components may behave differently on web vs mobile (e.g., touch vs mouse events, layout, accessibility). Tests that pass on web can fail on mobile (or in the mobile test environment) and vice versa. Achieving meaningful coverage across both platforms often means writing platform-specific test cases, duplicating setup and assertion logic.

11.5 Maintenance Overhead

Every new @platform component adds test surface for both implementations plus any shared components that use it. Refactoring a shared component can break tests in multiple places (web unit tests, mobile unit tests, integration tests). The testing headache compounds as the number of @platform components increases—roughly 2× the maintenance of a single-platform component library.

11.6 Shared Component Testing – Not Yet Validated

Important: Whether unit testing actually works for shared components in this setup has not been tested or validated. Shared components (DummyComponent, LargeComponent, PlotSearch) import from @platform/*, and it is unclear whether Jest, Vitest, or React Native test runners can correctly resolve these aliases and render shared components in isolation. Teams adopting this architecture should treat shared component unit testing as an open item and validate the approach early—including alias resolution, mocking strategy, and cross-platform test execution—before committing to the pattern.

12. Native Modules and Platform-Only Features

Mobile supports native modules (e.g., Camera, GPS, biometrics, file system access) that have no direct web equivalent. The current @platform architecture does not define how these should be handled.

12.1 The Problem

A component that uses the device Camera on mobile cannot be a straightforward @platform component—web has no native Camera API in the same sense (it uses getUserMedia or file input). If a shared component or screen needs camera access, the resolution strategy is undefined: should there be a mobile-only implementation, a web fallback (e.g., file upload), or conditional logic inside a shared component?

12.2 Possible Approaches

  • Platform-only components: Keep Camera (and similar features) as mobile-only components, not in @platform. Screens that need camera would import the mobile implementation directly and use a different flow on web.
  • Abstraction layer with platform-specific implementations: Create a @platform/CameraCapture where the mobile implementation uses the native Camera module and the web implementation uses input type="file" or getUserMedia. The shared API would hide the platform difference behind a common props contract.
  • Runtime detection and fallbacks: Shared components could detect the platform and render a mobile-specific child on native and a web-specific child (or placeholder) on web. This adds branching logic and can complicate shared code.

12.3 Current State

The repository does not currently demonstrate handling of native modules or platform-only features. Teams will need to decide on a strategy (platform-only vs abstraction vs runtime branching) and document it. This gap can increase complexity when adding features that rely on capabilities available on only one platform.

13. New Developer Onboarding

13.1 Understanding Curve

Difficulty: Medium–High. A new developer needs to understand:

  1. Monorepo and npm workspaces
  2. Path aliases and how they differ per package
  3. The concept of "platform resolution" – one import, two implementations
  4. The role of shared/types and __platform_types__
  5. Why the mobile build script rewrites aliases
  6. The component addition workflow (7 steps)

Without documentation, this can take 1–2 weeks of exploration and trial-and-error.

13.2 Common Pitfalls

  • Adding a component to web but forgetting mobile (or vice versa), leading to runtime errors when the shared component is used on the missing platform.
  • Forgetting to run generate:platform-types and getting type errors in shared code.
  • Assuming @platform resolves the same in all contexts (it does not – shared uses __platform_types__ for type-checking).
  • Using platform-specific APIs (e.g., DOM or React Native APIs) inside a shared component that uses @platform imports – shared components must remain platform-agnostic.

13.3 Mitigations

  • Maintain this document and a short CONTRIBUTING.md with the component addition checklist.
  • Add a pre-commit or CI check that ensures every web/src/ui/X has a corresponding mobile/src/ui/X for components used in shared.
  • Run generate:platform-types as part of the build or a pre-publish hook.
  • Provide a template or script to scaffold a new @platform component.

14. Recommendations

  1. Document the mental model: Create a one-page diagram showing how @platform resolves in web vs mobile, and where shared code fits.
  2. Automate platform type generation: Run generate:platform-types automatically before builds or in CI.
  3. Add a scaffold script: A script that creates the type file, web component folder, mobile component folder, and updates index files would reduce errors and save time.
  4. Enforce symmetry: Use lint rules or CI to ensure platform components exist in pairs when referenced by shared components.
  5. Consider alternatives for simple cases: For components with little shared logic, maintaining two separate implementations without @platform may be simpler. Reserve @platform for components that truly benefit from shared business logic.
  6. Validate shared component testing early: Confirm that unit tests can run for shared components with @platform imports before scaling the pattern. Document the test setup (alias resolution, mocks) for future developers.
  7. Define a strategy for native modules: Establish and document how platform-only features (Camera, GPS, etc.) will be handled—platform-only components, abstraction layers, or runtime fallbacks—before building features that depend on them.
